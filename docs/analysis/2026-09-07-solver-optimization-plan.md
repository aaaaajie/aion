# 云端解题提示词与 Skills 优化实施计划

日期：2026-09-07。状态：待实施；本次交付为计划。

## 目标与依据

降低无信息探索、错误前提继承和工具发现成本，提升不同题型下的稳定性。优先修改 Solver 决策提示、记忆摘要和现有 Skills，沿用现有运行架构。

依据：关联任务《制定云端解题进度修正计划》、[多轮对比记录](2026-09-07-solver-skill-comparison.md)，以及本地提示词、Skill 目录和评估脚本的核对。本次未重新拉取云端日志；“最新轮”专指对比记录中的 02:07 快照，不能作为当前云端状态。

- 对比记录中的成功轮与停滞快照使用相同 release、相同 Skill catalog，均未显式激活 Skill。因此尚无证据证明 Skill 内容本身造成了耗时差异。
- 12分41秒未完成是中途观察；a05 成功轮耗时17分28秒，不能将这份快照记为三题最终失败。
- 当前 Solver 和记忆提示已包含有效实验、最短目标检查、路径保留等要求。主要工作是消除重复与冲突、明确触发，并验证行为是否改变。
- 现有 `replay_solver_decisions.py` 明确禁用工具，且直接拼接三份 Skill 正文；它只能评价单轮回答，不能证明自主检索、激活或压缩后的执行有效。

## 阶段一：固定基线与验收样例

交付：当前工作树的相关文件快照、内容指纹、脱敏样例和评分定义。

1. 保存实际工作树中的提示词、Skill 内容、目录指纹、模型参数和测试版本。工作区已有大量未提交修改，不能把 HEAD 当作当前运行基线，也不覆盖已有修改。
2. 从历史分岔提炼六类样例：启动期连接失败、持续页面错误、局部阴性、文档与实际行为冲突、获得新能力后仍重复探索、会话被并发操作改变。
3. 每类准备一个开发样例、一个留出样例，共12个。只提供决策点之前的信息，删除题号、地址、答案、凭据和成功路线；留出样例改变业务描述和证据组合。
4. 同时保留不需要 Skill 的简单样例，防止把激活次数当作收益。

验收：每个样例具有可观察的预期行为与反例，评分依据不进入模型输入。历史 Solver 自述必须标明来源，不能冒充工具证据。

## 阶段二：统一决策与记忆规则（P0）

涉及 `agent/prompts/solver_system.txt`、`session_memory_system.txt`、`tool_surface_system.txt`；检查 Worker 提示是否存在相同冲突，仅同步共用原则。

### Solver：替换重复段落

保留四条短规则：

1. 观察、假设、有效阴性分开记录。阴性仅约束已测条件；请求未执行、会话失效、输出未读和客户端未验证均为未定。
2. 同一假设两次有效实验没有新信息，先复盘前提；若相关 Skill 尚未激活，用当前现象和未决问题检索并加载匹配项，再决定是否继续。已激活时使用其相关分支或资源；无匹配时说明下一项实验的区分能力。
3. 新能力或环境变化出现后，重新比较证据支持的目标验证与当前分支；只复验受变化影响的前提。
4. 注释、迁移说明和观察器建议属于线索，必须通过当前证据判断依赖关系，不能默认整条业务链为必经路线。

停滞与实验有效性继续分开：连续无效实验需要修复执行前提，不能靠换工具、改措辞或重建环境清空停滞。已有 `solver_review` 契约不新增门禁。

### 记忆：在原有八个标题内保存证据边界

采用紧凑条目：`观察/结论类型；来源；适用条件；未决前提；下一步`。仅保存会影响判断的条件，不要求每条穷举全部字段。

- 保留已验证能力、精确产物路径与已读范围、原假设和反证条件。
- 禁止将一次失败改写成永久限制，将局部无差异改写成全局排除。
- 证据撤销时同步撤销依赖结论；环境变化使相关结论待复验，不抹掉所有历史。
- 沿用现有标题、预算和状态权威来源，不新增记忆 schema 或兼容层。

### 工具入口：写清发现与激活链

明确通过 `tool_search(name=...)` 取得 `skill_search`、`skill_invoke` 的真实 schema，下一轮直接调用对应原生函数；Skill ID 使用搜索返回值。资源按实际工具 schema 读取，不猜参数。

第一版保持现有网关和按需激活机制。只有真实工具回放证明发现入口仍是阻塞，才另做直接暴露搜索/激活工具的单变量实验。

验收：修改后核心提示总量不超过修改前；压缩前后关键结论的确定性和覆盖范围一致；触发场景出现真实调用回执，简单场景无需仪式性加载。

## 阶段三：修订现有 Skills（P1）

统一为触发条件、前置条件、判断分支、无效实验、停止条件、工具入口。通用决策由提示词负责，领域细节由 Skill 负责，长例子放 references。

| 现有 Skill | 修改重点 | 应删除或替换的旧倾向 |
| --- | --- | --- |
| common/web-ctf-flow | 区分请求处理、认证、页面和业务结果；建立正常对照；隔离业务会话与扫描会话 | 过度围绕单一模板场景的主体组织 |
| execution/sqli-sql-injection | 先判定请求和对照是否有效；阴性保留范围；工具按证据选择 | 因可复现参数就固定调用工具；按手工/工具拆成两个假设 |
| execution/src-audit-workflow | 支持局部源码；记录已知入口、引用关系、缺失文件与待验证推断 | 将完整仓库清单作为所有场景前提 |
| execution/api-auth-and-jwt-abuse | 区分文档描述与运行事实；先确认依赖及对照 | 把迁移线索等同于当前实现或已确认问题 |
| execution/internal-network-recon | 区分启动暂态、客户端错误和持续不可达；同条件复验 | 从一次连接失败推断长期全局限制 |

第一批先交付 Web 流程、局部源码与阴性范围三项，验证后再修认证和网络两项。协议参考仅在现有工具文档不能回答实际问题时补充，不新增总纲型 Skill。

验收：关键分支确实出现在 Catalog 编译后的 activation view 中；遵守现有单 Skill 6000字符、活动上下文16000字符上限；搜索摘要足以匹配症状；无题目答案或实例专用路线。检查引用文档，删除与新主体冲突的旧要求。

## 阶段四：行为验证与云端对照（P0/P1共同出口）

按顺序验证，每层通过后才增加下一层：

1. **静态契约**：定向检查提示装配、Skill 搜索/激活、角色权限、内容预算及引用资源。复用现有测试，避免仅断言某句话存在。
2. **单轮决策**：复用 `scripts/replay_solver_decisions.py` 比较基线与新版；将显式注入 Skill 的组标注为内容实验，不能计作发现成功。
3. **真实工具闭环**：复用现有 Runner、ToolRegistry、SkillSessionContext，提供本地合成结果，记录搜索→激活→依据 Skill 行动的事件。加入“已有相关 Skill”“无匹配 Skill”和“无需 Skill”场景。扩展现有评估脚本，不另建框架。
4. **压缩闭环**：经过实际 summarizer 生成记忆，再让 Solver 继续；检查是否继承了错误确定性、丢失来源或重复读取已覆盖产物。
5. **授权基准运行**：同模型、预算、工具与目标初始化条件，交错执行基线/新版。先选3个代表场景，每版各3次，共18次，小样本筛查通过后再扩大。

对照先比较原版 A 与仅提示/入口修改 B；B通过后比较 B 与 Skill 内容修改 C，避免一次修改全部组件却无法判断收益。留出样例锁定，不能边看结果边改答案标准。

### 指标与推进门槛

- 硬性要求：样例中无证据越界扩大结论；压缩后无确定性升级；目录、权限与激活持久化契约通过。
- 触发质量：应检索场景的真实检索/激活比例，以及不应检索场景的多余调用数；加载次数本身不是目标。
- 过程效率：到下一项有效区分实验的时间、重复实验比例、无效实验比例、读取浪费、token 与总工具调用。
- 结果效率：固定时间预算内完成率、完成耗时中位数及全部运行明细。未完成运行按预算截尾并单列，不能从耗时统计中隐去。
- 初始业务目标：重复实验比例相对下降20%，完成率不下降；这是待验证目标，不是已有收益。18次仅用于发现明显退步，不据此宣称统计显著；分歧大时增加重复。

若提示变化通过但 Skill 无调用，先定位搜索可见性、匹配结果或激活失败，再决定是否改入口。若真实工具失败导致实验无效，单独记录工程缺陷，不用加提示掩盖。

## 交付顺序与范围

1. 基线快照、12个分岔样例与评分表。
2. 精简 Solver/记忆/入口提示和定向结果。
3. 首批三个 Skill 修订、真实调用与压缩闭环报告。
4. 后续两个 Skill 修订、配对运行报告和是否发布的结论。

本计划不包含观察器重构、结果投影重构或重新设计调度器；已有运行时修正继续作为基线。实现阶段按适用流程读取 Skill 编写规范，直接更新现有文件，移除冲突旧规则。发布独立候选版本，失败时切回完整基线版本，不增加运行时兼容分支。
